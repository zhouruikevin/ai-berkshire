## T2 · 多 Agent 对抗设计(★3,补考未答)

### 错点 1:后台 Agent 为什么必须**事前**做 WebSearch 预检
- ❌ 我答:"SubAgent 权限都处理会让流程**异常复杂**"(归因成复杂度权衡)
- ✅ 正确:不是"太复杂不处理",是**结构上根本弹不了框**。后台 Agent(`run_in_background: true`)没有和用户的交互通道,遇到权限问题**无法弹出交互式确认**(源码 L43)。≈ 子线程不能直接弹 UI 对话框。
- 🧠 记忆:**弹不了框 → 只能事前拦,启动后就来不及了。**

### 错点 2:静默拦截 + 兜底设计(Q3 第二问漏答)
- ❌ 我答:失败链路补对了,但**"源码用什么兜底设计"整段没答**。
- ✅ 正确:**两道防线**——
  1. **事前预检(主防线,L46-52)**:启动前 `grep '"WebSearch"' settings.local.json`,没命中就**停下、根本不启动 Agent**。
  2. **事中兜底(保险,L139「联网失败禁止伪装」)**:每个 Agent 的 prompt 硬编码——若搜索被拦截,**禁止用训练知识冒充**,必须在报告顶部标「⚠️ 未联网,基于训练知识,置信度降级」并如实告知 team-lead。
- 🧠 记忆:**①挡在门外(最优),②漏了也要"诚实地失败"而非"体面地造假"。**

### 错点 3:并行的深层动机(Q4 题眼,连着两次没抓到)
- ❌ 我答:"team 除了并行(=快)没比 research 多什么"
- ✅ 正确:**并行本身就是对抗的工程实现**。单 Agent 串行的致命弱点是**自我锚定**(第 2 步判"好生意",第 4 步逆向找死因时已经懒得反驳自己)。4 个 Agent **上下文隔离、互不通信**,risk-assessor 从没看过 business-analyst 的乐观结论 → **天然不被锚定**;team-lead 再把 4 份独立判断摆成 Bull vs Bear(L182),冲突自然浮现。
- 🧠 记忆:**对抗不靠"让 Agent 互喷",靠"让它们互相看不见"。** 另:team 每个 Agent 的 spec 反而比 research 薄;team 成本 ≈ 4 倍。

## T3 · 数据严谨性工程(Decimal)(★3,升★4路径:跑动手命令)

### 错点 4:financial_rigor.py 第 6 个子命令
- ❌ 我答:"通过历史推算 + 同行对比 + 第三方研报推算估值边际"(那是 `valuation_percentile.py` 干的活)
- ✅ 正确:第 6 个是 **`three-scenario` 三情景估值**(L340-373):给定乐观/中性/悲观三组「增速 + 目标 PE」,精确算 `未来EPS = 当前EPS×(1+增速)^年数` → `目标价 = 未来EPS×目标PE` → 涨跌幅。
- 🧠 记忆:**假设(增速/PE)由人给,计算(复利/乘法)交给确定性脚本。** 6 命令:verify-market-cap / verify-valuation / cross-validate / benford / calc / **three-scenario**。

### 错点 5:为什么 `Decimal(str(value))` 而非 `Decimal(value)`
- ❌ 我答:"经过**多次复杂计算**可能失真"(以为是累积误差)
- ✅ 正确:**问题在构造那一刻就已经脏了,不是算多了才脏**。`Decimal(0.1)` 会把 float 的二进制误差原样搬进来 → `Decimal('0.1000000000000000055...')`;`Decimal(str(0.1))` 先得到干净字符串 `"0.1"` 再构造 → 精确 `Decimal('0.1')`。`str()` 是**入口净化**,修的是输入边界。
- 🧠 记忆:**别 `new BigDecimal(double)`,要 `BigDecimal.valueOf(x)` / `new BigDecimal(String.valueOf(x))`——同一个坑。**

### 错点 6:偏差阈值符号(Q2 第二问漏答)
- ❌ 我答:漏答。
- ✅ 正确(L81-103):**>5% → ❌**(必须排查才能继续);**>1% 且 ≤5% → ⚠️**(可接受,可能因股价/股本波动);**≤1% → ✅**。
- 🧠 记忆:**5 红 1 黄,1 以内绿。** 彩蛋:Windows GBK 下这几个 emoji 会 `UnicodeEncodeError`——别让报警器自己先烧了(L60)。

### 错点 7:report_audit.py 三步流程
- ❌ 我答:"**标准化处理**(全角半角) → 抽样 15% → **去其他源验证**"(编了标准化步,漏了判决步)
- ✅ 正确:**Step1 抽样(`extract`)**:提取全部数据点 → 随机抽 15% → 输出含空 `fetched_value` 的 JSON 模板;**Step2 取数(人/Agent)**:按 financial-data 规范从可靠信源取数填入;**Step3 判决(`verdict`)**:比对偏差 ≤1% → 输出【准出】/【打回】。抽样量 `max(3, min(30, ...))`(最少 3 最多 30)。
- 🧠 记忆:**抽 → 取 → 判**;最关键是 Step3 判决(质量门禁本身),我漏的就是它。"标准化"顶多是 extract 内部细节,不是主流程步。

### 错点 8:verdict 退出码
- ❌ 我答:"失败时退出"(没说是几);理由说成"证明中间计算有问题"
- ✅ 正确(L546):**PASS→0,FAIL→1**。设计理由是**「可接 CI」**——退出码 1 是自动化/流水线的标准失败信号,能被 CI 捕获并**自动阻断报告发布**,不靠人读文字判断。
- 🧠 记忆:**门禁靠退出码,不靠人眼。0 过 1 挡。**

## 复盘:我的错误模式

- **大局观「为什么」很稳**(如"为什么不能直接问 AI 算"),但**机制实现细节**易错:归因方向(结构限制 vs 复杂度)、流程结构(漏关键步)、精确数值(退出码/阈值)。
- **改进**:读源码时不仅读"做什么",要读**"分几步、每步的名字、边界值、退出码"**;动手跑一遍命令看真实输出,比默读记得牢。
